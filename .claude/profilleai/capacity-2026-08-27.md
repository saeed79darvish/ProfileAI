# Capacity: where the platform saturates, and why

**Date:** 2026-08-27 · **Target:** api.profilleai.com (production) ·
**Traffic:** anonymous, read-only browsing · **Requests:** ~33,000 ·
**AI spend:** none

Question asked: *does the platform work if 1000 users start using it
concurrently?*

**Answer: no. The comfortable limit is about 200 concurrent users.**

---

## 1. What was measured

Seven staged runs against the live API, each a separate short run with a
watchdog that pulls load off as soon as the service starts to hurt.

| Concurrent | req/s | p50 | p95 | p99 | `/health` p95 | Errors |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 25 | 11.9 | 57ms | 221ms | 291ms | 224ms | 0 |
| 50 | 40.3 | 50ms | 77ms | 153ms | 73ms | 0 |
| 120 | 88.6 | 55ms | 291ms | 445ms | 162ms | 0 |
| 200 | 140.6 | 60ms | 349ms | 1,487ms | 212ms | 0 |
| 400 | 185.6 | 131ms | 2,152ms | 3,373ms | 1,931ms | 0 |
| 800 | 187.8 | 253ms | 9,218ms | 9,821ms | 4,026ms | 2.6% — 502 |
| 1000 | 189.9 | 396ms | 10,061ms | 10,927ms | 4,715ms | 2.9% — 502 |

Remote timings include ~50ms of network round-trip to the Oregon region.

Two things to read off this table:

- **Throughput stops at ~190 req/sec.** From 400 users onward, adding users
  adds nothing to throughput. 400 → 1000 is 2.5× the load for 2% more work
  done.
- **Latency absorbs everything after that.** p95 goes 349ms → 2.2s → 9.2s
  across three doublings, because once throughput is pinned, the only thing
  left that can move is queue depth.

Production recovered on its own within 25 seconds after each of the two runs
that produced 502s. It degrades and comes back; it does not stay down.

---

## 2. Which layer gives out

The `/health` column is the diagnostic. That endpoint touches no database and
does no work, so its latency is close to a pure reading of how long a request
waits before Node can even look at it.

- At 200 concurrent it answers in 212ms — about 50ms of that is network, so the
  process is keeping up.
- At 400 it takes **1.9 seconds**.
- At 800 it takes **4 seconds**.

None of that involves Postgres. The bottleneck is **CPU on a single Node
process**: `profilleai-api` runs one instance on a Render `starter` plan — half
a CPU core, no clustering — and Node executes JavaScript on one thread. 190
req/sec is what half a core is worth on this workload.

The database was never the constraint. It was barely touched: **96–100% of feed
responses came from the in-process 90-second cache.**

---

## 3. The important caveat

Every production stage was anonymous browsing, which is the cheapest path
through the API by a wide margin. Anonymous visitors:

- share a single response-cache key, so they nearly all hit cache;
- skip `authMiddleware`, which does a `User.findByPk` per request;
- skip profile-based ranking entirely and take the pure-recency query.

Signed-in traffic bypasses that cache by design — the key includes the user id
— so **real capacity for logged-in users is lower than 190 req/sec, and by how
much has not been measured on production.** Doing so needs seeded accounts
there, which do not exist.

Nothing here touched writes, uploads, resume parsing, or ApplyPilot. All are
heavier per request than anything measured.

## 4. What the test surfaced along the way

Two defects that have nothing to do with sizing, both since fixed. Full detail
in [bugs.md](bugs.md).

**Database errors were reported to users as "Token is not valid."** One catch
block in `middleware/auth.js` answered 401 for every failure and logged
nothing, so any database trouble silently logged signed-in users out. This
produced a 65% error rate in the first local run and was misdiagnosed as an
auth problem until the underlying Postgres error was found by hand.

**Rate limiting was keyed on a rotating proxy address.** With Cloudflare and
Render both in front and `trust proxy: 1`, `req.ip` was an intermediate address.
`ratelimit-remaining` was observed going 481 / 599 / 599 across consecutive
calls — the counter never accumulated, so the auth limiters protected nothing.
The inverse would have been worse: a stable intermediate address puts all users
in one 600-request bucket.

A third, in the dev database only: **3,957 indexes on `Users`** from repeated
`sync({ alter: true })`, enough that 20 concurrent queries exhausted Postgres's
lock table. Clearing 6,026 duplicates took the same local run from 65% errors
to zero errors at 150 concurrent with p95 of 42ms. Production is probably
clean; [bugs.md](bugs.md) carries the command to confirm.

---

## 5. What it takes to reach 1000

In priority order.

**1. Add CPU, in parallel.** The only thing that moves the 190 req/sec number,
and a spend decision rather than a code one. At the measured request rate, 1000
concurrent users generate roughly 700 req/sec — about four to five processes'
worth of capacity. That means more instances, or a plan with real cores plus
clustering. Clustering on the current half-core plan buys nothing, because
there is only one core to share.

**2. Fix the shared state before scaling out, not after.** Two things are
per-process today and quietly get worse with each instance added:
- the rate limiter's memory store — N instances grant every client N× the
  intended limit;
- `simpleCache` — each instance warms its own copy, so scaling out multiplies
  database load instead of dividing it.

**3. Then re-measure, against the database this time.** Once CPU stops being
the ceiling, Postgres becomes the next one. It is also on half a core, with a
pool of 10 per instance, and none of these runs came close to pushing it.

**4. And measure signed-in load.** The number that actually matters for
capacity planning is the one not yet collected.
